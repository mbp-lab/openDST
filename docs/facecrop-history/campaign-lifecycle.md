# Lifecycle ownership and proposal (workstream B)

Status: B1/B2 implemented with final focused/browser/JATOS evidence; physical-device coverage is deferred. The owner table and race traces below describe the pre-campaign extraction checkpoint 4fd85bc on 2026-10-06; the B1 section records the current coordinator change. Cancellation keeps the campaign policy: `cancel_no_video` submits the `save_without_video` marker, while aborting facecrop does not retract uploads already started or in flight. Withdrawal and remote deletion remain study policy.

## Transition and race traces

- **Prepare then start (introduction):** `WebcamCapture.onUserMedia` creates/registers a study handle and calls `prepare`; later `startRecordingInternal` starts MediaRecorder then calls handle `start`. Adapter start awaits the same memoized prepare, marks `started`, then calls session start. Session/controller each memoize prepare/start. This is intentionally idempotent, but the same operation lifecycle is represented at four layers.
- **Stop during preparation:** Main's cancellation or navigation invokes handle stop. Adapter stop queues a microtask, selects `session.dispose()` if `started` is false, which selects controller abort. In the controller, stop instead would set `stopping`, cancel the pending frame callback, and await `preparePromise`; abort terminates workers and waits prepare/start/in-flight jobs. Webcam wrapper also requests MediaRecorder stop and waits for both recorder stop and session stop. Existing tests cover recorder startup interrupted by study stop and study-level abort superseding a pending stop.
- **Stop during capture:** controller stop changes state to `stopping`, cancels the outstanding frame callback, waits the capture loop and in-flight processing, finishes assembly/encoding, drains sink writes and emits manifest before `terminal`. Main waits for handle stop before next-page advancement. MediaRecorder stop triggers ordinary-video upload independently; Webcam wrapper waits for recorder `onstop` as well as facecrop stop.
- **Abort during stop/upload:** public Session allows abort to replace its terminal promise while controller is not terminal. Controller abort cancels callbacks, clears/aborts sink queue and terminates workers; writes whose transport has already started may still resolve/reject. Study adapter strips artifact completion promises from its abort status notification, settles the session tracker as failed, and leaves per-write tracker outcomes observable. Tests establish that abort returns while a pending write remains unresolved; they do not establish remote retraction.
- **Unmount/cancel overlap:** `Main.componentWillUnmount` initiates abort of registered sessions. `WebcamCapture.componentWillUnmount` either starts stop or defers it when the cancellation ref is true; this avoids converting a selected withdrawal into a draining stop. The paths may race, so idempotency and the `faceCropSessions` identity check are important. Main removes a session after cleanup settles; WebcamCapture separately reports finished after stop/abort.
- **Navigation:** only page-boundary transitions wait on Main's registry. `faceCropNavigationPromise` suppresses duplicate advances during drain. Same-page slide transitions advance directly. The active-page unmount guard prevents a late drain from advancing after Main teardown.

## Filename reuse observation

The study derives `filenamePrefix` as `<studyResultId>_<studyPage>_<videoCounter>`. Facecrop artifact names append the unique capture ID plus segment/part identity, and manifests also contain that capture ID, so repeated facecrop captures with the same prefix do not by themselves reuse those artifact filenames. Ordinary MediaRecorder upload uses `<studyResultId>_<studyPage>_<videoCounter>.mp4` (or `.webm`) without a capture ID. If a study creates two ordinary recordings for the same page and counter, the filename is reused; `WebcamCapture.uploadVideo()` does not clear `recordedChunks` after upload, adding a separate repeated-recording concern. Current lifecycle tests confirm restart state reset but do not assert unique ordinary chunk names or chunk-list reset. Confirm whether same-counter repeated recordings are supported before changing this study schema; if they are, use an explicit study recording identity or guarantee counter advancement and add a regression.

## Proposal and decision

Keep the public library session as the sole owner of library terminal idempotency and controller resources. Keep the adapter responsible for study identity, transport/tracker and translating the marker policy; keep WebcamCapture as sole owner of MediaRecorder and Main as owner of navigation/withdrawal. Avoid method replacement in `registerFaceCropSession`: expose a study coordinator/wrapper that composes recorder stop and facecrop stop/abort while preserving a stable session handle, and make stop/abort policy explicit in that coordinator. Before implementation, first document and test the contracts rather than flattening the layers: the layers cross real ownership boundaries, while duplicate promise/state bookkeeping and mutation of the session object are the concrete complexity candidates.

Focused regressions should cover prepare-vs-stop, prepare-vs-abort, start-vs-stop before/after MediaRecorder start, repeated stop, abort superseding drain, unmount overlapping cancellation, navigation waiting once, and ordinary same-counter filename/chunk reuse. Retain the current marker semantics and verify that in-flight write tracker state remains visible after abort. The existing tests cover study abort over pending stop, recorder stop ordering, restart state reset, concurrent restart, startup interruption, registry abort/status history, and page-level cancellation selection; they do not cover the full cross-layer race matrix or ordinary filename reuse.

### B1 decision before implementation

Adopt an explicit component-owned capture coordinator. Registration creates a separate handle forwarding prepare/start and composing stop/abort with `stopMediaRecorder`; Main registers that handle and component cleanup uses the same identity. The original study session methods remain unchanged. This removes cross-owner mutation without flattening justified library/transport/navigation boundaries. No public library or stored schema/filename changes. Stop and abort still request recorder stop immediately, before awaiting library work; abort remains independent of network completion. Rejecting library cleanup must still await local recorder cleanup before surfacing its error. Tests must prove handle identity, original-method preservation, normal drain, abort superseding stop and rejection cleanup. Rollback returns registration to the previous wrapper mutation. Ordinary recording filename reuse is deferred pending evidence of supported repeated-counter recordings; it is a distinct study schema decision.

### B1 implementation checkpoint

Recorder cleanup starts immediately and completes even if library finalization rejects. ### Cancellation contract for the openDST study

“Cancel and submit data without video” submits the `save_without_video` marker and aborts new facecrop work. It does not retract recordings already uploaded or writes already in flight. A rejected upload remains uncertain; the study owns withdrawal, downstream interpretation of the marker and any remote deletion policy. Camera tracks are study-owned throughout. Normal page transitions await capture finalization; unmount cleanup is a fallback.

### B2 proposal: untransferred VideoFrame ownership

Source inspection found a cleanup gap beyond B1: `PipelineWorker.request` rejects closed-worker submissions and `pump` rejects a failed `postMessage`, while neither closes a frame whose transfer never succeeded. `fail` rejects queued requests without releasing their frame resources. The analysis worker's `finally frame.close()` cannot own a frame that never reached that worker. Adopt cleanup of request-owned frames on these pre-transfer failures; successful transfer continues to hand ownership to the worker. Alternatives are relying on GC (no explicit browser-resource guarantee) or closing every successful submitted frame on main as well (unnecessary cross-owner cleanup). No pixel/timing/schema/public export change is intended. Regression gates: failed postMessage, closed worker, queued request discarded after worker crash, and transferred pending requests must not be mistaken for untransferred queued frames. At this pre-implementation decision checkpoint, rebuild/browser evidence was still required; final results now include B2.

### B2 implementation checkpoint

The internal worker adapter now releases request-owned frames when a closed worker rejects a submission, native `postMessage` throws, or worker failure discards queued requests. A successfully transferred frame stays worker-owned; it is not closed again by this cleanup. The implementation class is exported only from the internal source module for regression access and is absent from `src/index.js`/the package API. Three focused ownership regressions pass; the controller/session/adapter focused selection totals 22 passing tests. Independent review found no ownership or public API regression. The final B2/A2 artifact subsequently passed the browser/JATOS gates linked in the acceptance report.

### Study history and lifecycle edge coverage

`Main.updateFaceCropCaptureStatus` stores the latest status snapshot for each `captureId`: repeated updates replace that capture's row, while distinct captures remain available in `studyMetaTracker.faceCropCapture.captures`. Status payloads contain capture identity/context, aggregate statistics, manifest and per-part artifact summaries; frame pixels and per-frame analysis arrays stay inside the capture/persistence pipeline and are not copied into this study history. The retention policy is latest status per capture plus the compact part/file summaries that status carries. It is intentionally proportional to captures and parts for the study lifetime; there is no invented participant-count or fixed-cap guarantee. Future schema changes that add per-frame data must be reviewed separately.

The initial synthetic history fixture was superseded by actual captured status/inventory replay. The final measurement and structural checks below describe the current regression; they do not establish a maximum study size or process-memory ceiling.

Additional lifecycle fixtures cover rejected prepare followed by disposal (the study tracker settles failed once), repeated public `stop()` sharing one terminal promise, and a page drain completing after unmount without advancing. Cancellation-selected WebcamCapture unmount defers its own stop so the study cancellation path remains authoritative. Existing tests also cover abort superseding a pending drain, recorder cleanup after rejected finalization, restart serialization, and page navigation waiting for drain. These are isolated contract tests; a physical-camera/unmount/navigation interleaving matrix remains outside mock coverage.
