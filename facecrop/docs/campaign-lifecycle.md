# Lifecycle ownership and proposal (workstream B)

Status: B1 implemented with focused validation; broader acceptance gates remain open. The owner table and race traces below describe the pre-campaign extraction checkpoint 4fd85bc on 2026-10-06; the B1 section records the current coordinator change. Cancellation keeps the campaign policy: `cancel_no_video` submits the `save_without_video` marker, while aborting facecrop does not retract uploads already started or in flight. Withdrawal and remote deletion remain host policy.

## Transition and race traces

- **Prepare then start (introduction):** `WebcamCapture.onUserMedia` creates/registers a host handle and calls `prepare`; later `startRecordingInternal` starts MediaRecorder then calls handle `start`. Adapter start awaits the same memoized prepare, marks `started`, then calls session start. Session/controller each memoize prepare/start. This is intentionally idempotent, but the same operation lifecycle is represented at four layers.
- **Stop during preparation:** Main's cancellation or navigation invokes handle stop. Adapter stop queues a microtask, selects `session.dispose()` if `started` is false, which selects controller abort. In the controller, stop instead would set `stopping`, cancel the pending frame callback, and await `preparePromise`; abort terminates workers and waits prepare/start/in-flight jobs. Webcam wrapper also requests MediaRecorder stop and waits for both recorder stop and session stop. Existing tests cover recorder startup interrupted by host stop and host-level abort superseding a pending stop.
- **Stop during capture:** controller stop changes state to `stopping`, cancels the outstanding frame callback, waits the capture loop and in-flight processing, finishes assembly/encoding, drains sink writes and emits manifest before `terminal`. Main waits for handle stop before next-page advancement. MediaRecorder stop triggers ordinary-video upload independently; Webcam wrapper waits for recorder `onstop` as well as facecrop stop.
- **Abort during stop/upload:** public Session allows abort to replace its terminal promise while controller is not terminal. Controller abort cancels callbacks, clears/aborts sink queue and terminates workers; writes whose transport has already started may still resolve/reject. Host adapter strips artifact completion promises from its abort status notification, settles the session tracker as failed, and leaves per-write tracker outcomes observable. Tests establish that abort returns while a pending write remains unresolved; they do not establish remote retraction.
- **Unmount/cancel overlap:** `Main.componentWillUnmount` initiates abort of registered sessions. `WebcamCapture.componentWillUnmount` either starts stop or defers it when the cancellation ref is true; this avoids converting a selected withdrawal into a draining stop. The paths may race, so idempotency and the `faceCropSessions` identity check are important. Main removes a session after cleanup settles; WebcamCapture separately reports finished after stop/abort.
- **Navigation:** only page-boundary transitions wait on Main's registry. `faceCropNavigationPromise` suppresses duplicate advances during drain. Same-page slide transitions advance directly. The active-page unmount guard prevents a late drain from advancing after Main teardown.

## Filename reuse observation

The host derives `filenamePrefix` as `<studyResultId>_<studyPage>_<videoCounter>`. Facecrop artifact names append the unique capture ID plus segment/part identity, and manifests also contain that capture ID, so repeated facecrop captures with the same prefix do not by themselves reuse those artifact filenames. Ordinary MediaRecorder upload uses `<studyResultId>_<studyPage>_<videoCounter>.mp4` (or `.webm`) without a capture ID. If a host creates two ordinary recordings for the same page and counter, the filename is reused; `WebcamCapture.uploadVideo()` does not clear `recordedChunks` after upload, adding a separate repeated-recording concern. Current lifecycle tests confirm restart state reset but do not assert unique ordinary chunk names or chunk-list reset. Confirm whether same-counter repeated recordings are supported before changing this study schema; if they are, use an explicit host recording identity or guarantee counter advancement and add a regression.

## Proposal and decision

Keep the public library session as the sole owner of library terminal idempotency and controller resources. Keep the adapter responsible for study identity, transport/tracker and translating the marker policy; keep WebcamCapture as sole owner of MediaRecorder and Main as owner of navigation/withdrawal. Avoid method replacement in `registerFaceCropSession`: expose a host coordinator/wrapper that composes recorder stop and facecrop stop/abort while preserving a stable session handle, and make stop/abort policy explicit in that coordinator. Before implementation, first document and test the contracts rather than flattening the layers: the layers cross real ownership boundaries, while duplicate promise/state bookkeeping and mutation of the session object are the concrete complexity candidates.

Focused regressions should cover prepare-vs-stop, prepare-vs-abort, start-vs-stop before/after MediaRecorder start, repeated stop, abort superseding drain, unmount overlapping cancellation, navigation waiting once, and ordinary same-counter filename/chunk reuse. Retain the current marker semantics and verify that in-flight write tracker state remains visible after abort. The existing tests cover host abort over pending stop, recorder stop ordering, restart state reset, concurrent restart, startup interruption, registry abort/status history, and page-level cancellation selection; they do not cover the full cross-layer race matrix or ordinary filename reuse.

### B1 decision before implementation

Adopt an explicit component-owned capture coordinator. Registration creates a separate handle forwarding prepare/start and composing stop/abort with `stopMediaRecorder`; Main registers that handle and component cleanup uses the same identity. The original host session methods remain unchanged. This removes cross-owner mutation without flattening justified library/transport/navigation boundaries. No public library or stored schema/filename changes. Stop and abort still request recorder stop immediately, before awaiting library work; abort remains independent of network completion. Rejecting library cleanup must still await local recorder cleanup before surfacing its error. Tests must prove handle identity, original-method preservation, normal drain, abort superseding stop and rejection cleanup. Rollback returns registration to the previous wrapper mutation. Ordinary recording filename reuse is deferred pending evidence of supported repeated-counter recordings; it is a distinct host schema decision.

### B1 implementation checkpoint

`WebcamCapture.registerFaceCropSession` now registers an explicit coordinator and keeps it as the component cleanup identity. The underlying session stop/abort methods are never reassigned. Recorder cleanup starts immediately and completes even if library finalization rejects. On Node 22.16.0, direct CRA test invocation (avoiding lifecycle build hooks) passed 13 tests in WebcamCapture lifecycle, Main facecrop and host adapter suites, including stable identity, pending-stop/abort and rejection cleanup regressions. This is focused mocked lifecycle evidence; sustained browser and actual JATOS cancellation gates remain open. The rest of the lifecycle layers are retained because they own distinct resources and host policy; no broad flattening is justified by current evidence.

### Cancellation contract for the openDST host

“Cancel and submit data without video” submits the `save_without_video` marker and aborts new facecrop work. It does not retract recordings already uploaded or writes already in flight. A rejected upload remains uncertain; the host owns withdrawal, downstream interpretation of the marker and any remote deletion policy. Camera tracks are host-owned throughout. Normal page transitions await capture finalization; unmount cleanup is a fallback.
